# The catalogue: where it lives and how it gets published

**Status:** built, 9 August 2026. Written after building the publish function
and then looking properly at what it was publishing into. §7 records how it
landed; §11 is what remains.

Replaced `docs/shelving-catalog-workflow.md`, which described the Dropbox folder
and "ask Codex to run the importer" flow the manager had already superseded.
See also `docs/studios.md` for the gate in front of all of this.

---

## 1. The problem, stated properly

The catalogue exists in **three places**, written by **two different paths**,
and nothing keeps them in agreement.

| Copy | Where | Written by | Read by |
|---|---|---|---|
| Editorial record | `catalog.json` in the repo | `catalog.command` | the build script |
| What the public sees | `const configurations = […]` baked into `shelving.html` | a **regex splice** into a 2,772-line HTML file | the page, at runtime, via JS |
| What the manager calls "live" | the `published` blob | **the ops runner**, separately, alongside performance stats | `catalog.html` |

*(Past tense as of 9 August 2026 — this section describes what was found, and
the rest of the document describes what replaced it.)*

The third row is the one that bites. `framework.co.ke/catalog.html` decides
whether to show you "2 staged changes" by comparing your draft against the
`published` blob — but that blob is pushed by `framework-ops/src/catalog.js`
during a stats sync, **not** by the publish that actually changes the site. Run
a publish without a stats sync afterwards and the manager is diffing against a
stale baseline: it will show staged changes that are already live, or none when
there are some.

Everything else follows from the second row. Because the public copy lives
inside an HTML file, publishing means rewriting that file; because the Meta feed
is generated by parsing that file back out again, publishing means regenerating
the feed too; and because all of that is file surgery, publishing needs
somewhere with a checkout — a laptop, or a function holding a repo-write token.

**The complexity is not in the publishing. It is in having three copies.**

---

## 2. Principles

1. **One published record.** The site reads it, the manager reads it, the feed
   derives from it. If two things can disagree about what is live, eventually
   they will, and nobody will know which is right.
2. **The editorial record is separate from the published artifact.** What we
   keep (every product, including retired ones, with notes and codes) is not
   what we serve (the active ones, with the fields a page needs).
3. **Content is data, not code.** A price list belongs in a JSON file, not in a
   JavaScript array literal inside a page, edited by regular expression.
4. **Publishing is deliberate and atomic.** Edits accumulate as a draft; one
   action makes them live; it either all lands or none of it does.
5. **Nothing derived is hand-maintained.** The feed and the public artifact are
   generated from the record every time, never edited.
6. **The live site survives a failed publish.** Validation happens before
   anything is written, and the previous deploy is always one click away.

## 3. Target architecture

```txt
        catalog.html (manager)                    shelving.html (public)
        edits, toggles, uploads                   fetches /data/catalog.json
                 │                                          ▲
                 │ draft                                    │
                 ▼                                          │
        ┌──────────────────┐                                │
        │  Netlify Blobs   │   draft            ┌───────────┴──────────┐
        │                  │   staged images    │  framework-site repo │
        │                  │   stats (runner)   │                      │
        └────────┬─────────┘                    │  catalog.json        │ editorial
                 │                              │  data/catalog.json   │ published
                 │  POST /api/catalog-publish   │  feeds/…csv          │ derived
                 └─────────────────────────────▶│  images/…            │
                                                └──────────┬───────────┘
                                                           │ push → Netlify deploys
                                                           ▼
                                                      framework.co.ke
```

### What each file is

| File | Role | Public | Written by |
|---|---|---|---|
| `catalog.json` | **Editorial record.** Every product, active or not, with `designCode` and anything else we want to keep | no — blocked by a redirect, as `/docs/*` and `/scripts/*` already are | publish |
| `data/catalog.json` | **Published artifact.** Active products only, projected to the fields a page needs, with a schema version | yes | publish |
| `feeds/meta-shelving-catalog.csv` | **Derived.** Meta fetches it on a schedule | yes | publish |
| `images/shelving/configs/…` | Product images and thumbnails | yes | publish |

`catalog.json` **was** served publicly — nothing in `netlify.toml` blocked it —
so the inactive product and its price were readable by anyone who looked. Small,
but the kind of thing that stops being small. Now blocked by a redirect.

### What the blobs are for, after this

Only three things, none of them "the catalogue":

- **`draft`** — edits not yet published. Unchanged.
- **staged images** — uploads not yet published. Unchanged.
- **`stats`** — per-product performance, pushed by the ops runner. Renamed from
  `published`, and reduced to *only* the stats.

One refinement on contact with the code: the manager takes its baseline from
`catalog.json` **imported directly into `/api/catalog`**, not from
`/data/catalog.json`. A function is bundled with the deploy, so that import is
exactly the catalogue the live site is serving — and unlike the public artifact
it still contains inactive products, which the manager needs in order to turn
them back on.

That rename is the fix for §1's third row: the runner stops having an opinion
about what the catalogue contains, and keeps the one it is qualified to have.

## 4. Publishing, step by step

`POST /api/catalog-publish`, with a dry run first (`?dry=1`) that does every
step except the write.

1. **Authorise.** Reject anything without the publish secret (§6).
2. **Read** the draft and the staged images from blobs; read `catalog.json` and
   the repo's file list from GitHub.
3. **Validate, before anything is written.**
   - the draft parses and every product has a unique id
   - every *active* product has at least one image
   - every image an active product names exists — already in the repo, or in
     this upload batch. A missing thumbnail counts.
   - prices are numbers; `priceValue` agrees with `price`
   Any failure returns the list and writes nothing.
4. **Build** the three files from the draft. Pure functions, no I/O, shared with
   the command-line path so both produce the same bytes.
5. **Write one commit** — blobs → tree → commit → ref, against the parent SHA
   read in step 2. One commit is one deploy; writing files one at a time is one
   deploy per file, and the site would be briefly live with a page that
   disagrees with its own data.
6. **On a non-fast-forward** (someone else published while this one was being
   reviewed) — do not force. Return "someone else published; reload and try
   again", keep the draft.
7. **Clear the draft and the staged images, only now.** A cleared draft with no
   commit behind it loses the work, which is much worse than publishing twice.
8. **Netlify deploys** on the push. One to two minutes.

### Failure modes

| What goes wrong | What happens |
|---|---|
| Missing image or thumbnail | Refused at step 3, listed by path, nothing written |
| Malformed draft | Refused at step 3 |
| Two people publish at once | Second one refused at step 6, draft intact, told to reload |
| GitHub unreachable / token expired | Refused, draft intact, error names the cause |
| Commit lands, blob clear fails | Site is correct; manager shows stale staged changes until reload. Harmless |
| Bad content published | Netlify deploy rollback (one click), or revert the commit |
| `data/catalog.json` fails to load in a browser | Page shows a retry message instead of an empty grid (§5) |

## 5. The public page

`shelving.html` fetches `/data/catalog.json` instead of carrying the array.

- **Preload it** — `<link rel="preload" as="fetch">` in the head, so it starts
  downloading with the HTML rather than after the script parses. This is what
  keeps the change from costing perceived speed.
- **Check the schema version** and refuse to render an incompatible one, rather
  than rendering something wrong.
- **Fail visibly, not silently.** If the fetch fails, show "couldn't load our
  range — retry" where the grid would be. An empty section that looks
  deliberate is the worst outcome.
- **Cache header:** `public, max-age=60, stale-while-revalidate=86400` in
  `netlify.toml`. Fast, and never more than a minute behind a publish.

**On SEO:** none is lost. The product grid and the `schema.org` microdata are
*already* built at runtime by JavaScript from the array
(`grid.innerHTML = configurations.map(…)`, `microdata.innerHTML = …`). There is
exactly one piece of static product markup in the served HTML, and it is inside
a template string. Google already executes JS to see any of this. The baked
array saves one same-origin request to a CDN-cached file — that is its entire
contribution, and it is not worth what it costs everywhere else.

## 6. Access, honestly

Today every catalogue endpoint is guarded by one shared secret passed **in the
query string** — the same secret as the read-only funnel dashboard. That means:
a secret that ends up in browser history and referrer headers; no way to give
someone read access without giving them publish; no way to revoke one person;
and no record of who published what.

At three people this is survivable, and rebuilding it as SSO would be the
expensive answer. Two proportionate fixes:

- **A separate publish secret, sent as a header**, not the query string. Reading
  the dashboard and changing prices should not be the same key, and secrets do
  not belong in URLs.
- **Ask who is publishing** — a name field in the manager, written into the
  commit message. That is the audit trail, free, and git keeps it forever.

The GitHub token stays fine-grained: Contents read/write on `framework-site`
only. That is the standard pattern for git-backed editing (it is what Decap and
TinaCMS do), not an unusual risk.

## 7. Migration — reversible at every step

Nothing here is a big-bang, and every step is independently deployable.

| # | Step | Reversible by |
|---|---|---|
| 1 | Publish `data/catalog.json` **alongside** the existing baked array. No reader yet | deleting the file |
| 2 | Point the manager's baseline at `/data/catalog.json`; runner's blob becomes `stats` only | reverting one fetch |
| 3 | `shelving.html` fetches, **falling back to the baked array** if the fetch fails | the fallback is already the old behaviour |
| 4 | Delete the baked array and the splice, once step 3 is observed working | git revert |
| 5 | Block `/catalog.json`; add the cache header; record who published | one redirect |

Step 3 is the only one that touches the public product page, and it ships with
the old path still in place underneath it. Step 4 is the point of no return, and
it is a deletion, taken only once step 3 has been observed working.

**All five landed.** Step 3 was verified by serving a deliberately altered
`data/catalog.json` and watching the page render it — three products with a
changed title, matching microdata, "see more" correctly hidden — then by
breaking the file in three ways (bad schema, 404, and 404 with the array
already gone) and confirming the fallback, then the failure message. Step 4
removed 342 lines of baked array from `shelving.html`.

Publishing writes data, not markup: the function no longer reads or writes
`shelving.html` at all, and `buildPublish` refuses to emit an HTML file — there
is a test that asserts it.

## 8. What this deletes

- the regex splice into `shelving.html`, and the ~340-line array it maintains
- `readConfigurations` — parsing the array back out of the HTML
- `generate-meta-catalog-feed.mjs`'s round trip through generated HTML
- `build-catalog.mjs`'s page-writing job
- the publish function's read of `shelving.html`, and one whole class of failure
- the third copy of the catalogue, and the stale-baseline bug in §1

`catalog-build.mjs` keeps the projection, the feed and the validation, and loses
the splice. The publish function keeps its shape and gets shorter.

The honest accounting: this is perhaps a 30% line reduction, and a much larger
reduction in the number of things that can silently disagree. The second number
is the one worth having.

## 9. Deliberately not doing

- **A headless CMS** (Sanity, Contentful, Decap). They would handle products and
  images well, but all of them would replace the manager — and the manager is
  not a product editor, it is a product editor *plus* per-product seen / opened
  / handoffs / conversations / sales / revenue wired to our own funnel data. No
  CMS gives that. Buying one to get a publish button is a bad trade.
- **An image CDN** (Cloudinary et al). Committed images on Netlify's CDN are
  already fast, free and permanent, and transforms are not needed.
- **Instant publishing** (content served from blobs at request time). It would
  remove the deploy wait and the token, but it costs a runtime dependency on
  every page view and, more importantly, the catalogue's history. A price list
  wants to be diffable and attributable; git gives that for nothing.
- **A build step.** The site has none, and the publish artifacts are generated
  by the publisher rather than at deploy time, so it still needs none.
- **SSO / per-user accounts.** Disproportionate at this size; §6 is the
  proportionate version.

## 10. What is not done

- **`GITHUB_TOKEN` and `GITHUB_REPO`** are still unset, so `/api/catalog-publish`
  answers 501 and the Publish dialog shows the `catalog.command` instructions.
  That is the fallback working as intended.
- **The publish secret is still the page-login secret.** The shared key has
  since been split in two — `SITE_LOGIN_KEY` for people, `SITE_EXPORT_KEY` for
  the ops runner, which alone opens `/api/export`, `/api/dashboard-data` and
  `/api/catalog-data` — and the key now travels in a header, so the query-string
  half of §6 is done. But that split is by *caller*, not by *capability*: anyone
  who can open the manager can still publish, which is the half of §6 that
  matters here. The `by=` name in the commit message shipped. A publish-only
  secret stands as the next thing to do.
- **Nobody has watched a real publish.** The pure half is tested; the commit
  half has never run against the real repository, because doing that is a
  production write.

---

## 11. Effort

About a day, spread across the five migration steps, most of it in step 3 and in
watching step 4. Steps 1, 2 and 5 are an hour or two each.

The publish function, the shared build module, the browser-side resizing and the
manager's editing fixes already exist — this reshapes what they operate on
rather than replacing them.
